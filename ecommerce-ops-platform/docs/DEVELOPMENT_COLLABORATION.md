# 后续开发协作规范

本文档记录本项目后续和 AI 编程助手协作的推荐方式，目标是减少上下文、避免跨模块误改、保持目录和代码清晰。

## 1. 推荐任务格式

以后给开发任务时，优先使用以下 6 项：

```text
模块：
范围：
目标：
禁止：
验收：
执行：
```

示例：

```text
模块：图片生产 / 产品资料
范围：只改产品资料页面和对应后端接口
目标：模板中可以新增、删除自定义字段；产品档案按模板字段填写
禁止：不要改拍摄分组、不要改视频生产、不要改模型配置
验收：
1. 可以创建字段
2. 可以删除字段
3. 产品档案填写区显示模板字段
4. 删除字段后旧档案不报错
执行：修改代码，跑测试，不提交 GitHub
```

- 运营中心 / 投流复盘
- 运营中心 / 库存利润
- 运营中心 / 日报周报
- 采后中心 / 供应商库
- 采后中心 / 授权凭证

### 范围

说明允许阅读和修改哪些区域。范围越清楚，越能减少上下文。

推荐写法：

```text
范围：只改前端产品资料页面、平台模板接口和相关测试。
```

### 目标

说明用户最终要看到什么业务结果，不只描述按钮或代码。

推荐写法：

```text
目标：用户可以在模板里新增字段，并在产品档案里按这些字段批量填写。
```

### 禁止

说明本次不能动什么，防止顺手重构导致新问题。

推荐写法：

```text
禁止：不要改拍摄分组，不要恢复 AI 自动分组，不要改视频生产。
```

### 验收

说明完成标准。验收越具体，越容易一次做对。

推荐写法：

```text
验收：
1. 新建字段后刷新页面仍存在
2. 删除字段后产品档案页面不报错
3. 批量修改只影响勾选产品
```

### 执行

说明是否只分析、是否修改代码、是否跑测试、是否提交和推送。

推荐写法：

```text
执行：修改代码，跑后端测试和前端构建，不提交 GitHub。
```

或：

```text
执行：只分析问题，不改代码。
```

## 3. 如果需求还没想清楚

可以先让助手拆任务，不直接开发：

```text
你先帮我拆成模块、范围、目标、禁止、验收、执行，再开发。
```

如果业务流程本身还不确定，先要求逐句确认：

```text
我重新描述需求，你不清楚的逐句问我，先不要写代码。
```

## 4. 前端细节修改沟通格式

前端要改按钮、文本、对齐、间距、弹窗、缩略图、表格列等细节时，优先用以下格式。用户不需要知道代码文件名，但需要帮助定位界面元素。

```text
前端修改：
页面：
区域：
元素文字：
当前问题：
期望效果：
不要动：
验收：
执行：
```

示例：

```text
前端修改：
页面：图片生产 / 产品资料
区域：产品清单
元素文字：删除
当前问题：删除弹窗里的复选框很奇怪，布局不协调
期望效果：去掉复选框，说明文字居左，取消和确认按钮右对齐
不要动：不要改删除产品的后台逻辑
验收：
1. 弹窗没有复选框
2. 按钮右对齐
3. 删除逻辑和原来一致
执行：只改前端，跑前端构建，不提交 GitHub
```

如果有截图，推荐写法：

```text
看截图红框区域：
页面：图片生产 / 拍摄分组
区域：待分配原始照片
元素：缩略图右上角删除按钮
当前问题：按钮离图片太远，外框过大
期望效果：按钮贴合缩略图右上角，缩略图完整显示，不裁切
不要动：不要改产品资料、不要改后端接口
```

前端定位最有用的信息：

- 一级菜单：运营中心 / 视频生产 / 图片生产 / 模型配置。
- 二级页面：例如拍摄分组、产品资料、出图方案、结果审核、导出上传。
- 区域名称：例如待分配原始照片、产品清单、模板字段、任务列表。
- 元素文字：按钮文字、标题、提示语、表格列名、弹窗标题。
- 当前问题：错位、太大、太小、被遮挡、不对齐、提示文案不对、交互不符合预期。
- 期望效果：改到什么位置、什么大小、什么对齐方式、哪些内容显示或隐藏。
- 限制范围：只改样式、只改文案、只改这个页面，还是允许改组件结构。

如果无法描述元素名称，可以直接说“截图中红框/箭头指的地方”。开发时应结合页面文字、DOM、组件文件和样式文件定位，避免跨模块搜索后顺手修改无关区域。

## 5. 解耦原则

后续开发默认遵守：

- 一个任务只处理一个模块。
- 不把多个业务模块塞进同一个超大文件。
- 新代码优先放进模块目录，旧入口只保留兼容转发。
- 高容量列表和表格使用主工作区，不放窄侧栏。
- 运行数据、上传文件、数据库、缓存、临时文件放到 `ops-workbench-runtime/`，不混入代码目录。
- 文档和代码同时更新；业务口径变更必须同步更新交接文档或模块文档。
- 不恢复已经明确废弃的旧功能和旧命名。

## 7. 推荐交付要求

开发类任务建议明确要求：

```text
验收：
1. 后端测试通过
2. 前端构建通过
3. 如果涉及交互，说明是否做了真实浏览器验证
4. 提交前列出改动文件
执行：修改代码，跑测试，提交 GitHub
```

如果不希望上传：

```text
执行：修改代码并测试，但不要 commit，不要 push。
```

如果只想检查：

```text
执行：只读检查，输出问题清单和建议，不修改文件。
```

## 8. Git 和安全约定

- 提交前先检查 `git status`。
- 不提交 `.env`、API Key、数据库、上传素材、AI 结果、缓存、`node_modules`。
- GitHub token、百炼 API Key 等密钥只应保存在本机运行环境或 GitHub Secrets，不写入仓库文档和代码。
- 需要推送 GitHub、改仓库设置、打标签时，单独说明。
- 如果曾在聊天中暴露 token，应立即在 GitHub 后台吊销并重新生成。
